# Message Helper 需求背景与产品需求

日期：2026-10-21。本文作为 Mac 本地开发的产品需求基线。用户已确认 macOS 优先及“快捷键拦截＋发送按钮蒙版”方案；具体客户端兼容性仍需真机验证。

## 1. 背景与目标

用户在即时通信中可能因为错别字、病句、多重否定、指代不清、英语语法或措辞问题产生误解。把消息复制到 AI 工具再贴回聊天框，操作成本较高，也容易在修正后继续编辑而遗漏检查。

产品希望在用户的原有聊天流程中提供三个连续环节：实时检测、发送前检查、用户确认的语句修正。最初目标包含短信、微信、飞书、钉钉等移动场景；经过平台能力讨论，首发调整为 macOS 桌面应用，采用快捷键拦截与发送按钮蒙版。移动端及其他桌面平台不是当前实现范围。

产品是用户自愿启用的表达辅助工具，不是不可绕过的企业消息审计或防泄漏系统。不承诺所有应用、所有发送方式均可拦截。

## 2. 目标场景

用户已要求以下三类场景都需支持，不能只覆盖其中一种：

| 场景 | 重点 | 判断边界 |
| --- | --- | --- |
| 中文职场沟通 | 病句、责任和时间表达歧义、可选措辞建议 | 礼貌程度不是客观语法错误 |
| 日常中文聊天 | 错别字、影响理解的表达 | 允许口语、省略、表情、方言，不强制改成书面语 |
| 英语及中英混合 | 语法、拼写、用词及混合表达 | 保留专名、代码、链接，不擅自翻译整句 |

首个适配应用暂定 macOS 微信，后续按独立适配器扩展飞书、钉钉。该优先顺序不代表已经证明微信接口可用。各语言场景的效果都需独立评估。

## 3. 市场与竞品背景

主要替代方案：搜狗、讯飞、微信输入法等输入工具；Grammarly、SwiftKey、LanguageTool 等校对或输入产品；ChatGPT、豆包等通用助手；通信平台内置的写作辅助。

需要验证的竞争优势是：在消息发送现场低成本发现值得修改的问题，少误报、不改变原意、无需反复复制。不能仅凭“大模型可以改写”认定存在产品壁垒，也不能仅凭用户聊天频繁认定有付费意愿。

本轮访问官方资料和竞品网站遭网络代理 403，未完成当前版本实测、价格验证、用户访谈或市场规模统计。上述名单是研究线索，不是已核实功能清单。初步分析和资料入口见 [产品发现初稿](research/2026-10-21-product-discovery.md)。

后续用同一批脱敏消息对比：发现有效问题的比例、正确口语被误报的比例、意图保留、操作步骤、延迟、隐私设置和费用。访谈需关注真实错误经历及用户对跨应用读取草稿、系统权限的接受度。

## 4. 核心用户流程

1. 用户启用目标应用保护，并授予必要系统权限。
2. 助手识别受支持的聊天输入框、会话和发送按钮，显示“已保护”；不能识别时显示具体不可用原因。
3. 草稿停顿后可以实时检查，但拼音组合输入期间不触发替换；实时结果仅作提醒，不构成永久放行。
4. 用户点击发送按钮或使用已适配的发送快捷键，助手接住本次操作，取得最新草稿快照并校验。
5. 无问题时复核原会话和草稿后发送一次；有问题时展示原文、原因、修正建议及“采纳并重新检查／仍然发送／取消”。
6. 校验期间继续编辑、切换会话或目标失效，旧结果及发送授权立即失效。
7. 每次实际发送都需要新的一次性授权，不能在检查后持续撤去蒙版。

## 5. 功能需求与验收

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| FR-01 | 目标识别 | 只有可识别窗口、会话、编辑框及发送模式时显示已保护；其他窗口不受影响 |
| FR-02 | 鼠标入口 | 蒙版只覆盖目标发送按钮；点击进入统一校验流程，不让首次点击直接穿透 |
| FR-03 | 键盘入口 | 仅拦截目标输入框中配置的发送快捷键，中文候选确认、换行和其他应用快捷键保持正常 |
| FR-04 | 实时提醒 | 输入停顿后检查文本快照；过期回调不能覆盖新结果，不在组合输入中修改文本 |
| FR-05 | 问题分层 | 区分语法／错字、歧义及可选润色，提供解释，不武断替用户决定原意 |
| FR-06 | 确认修正 | 仅替换用户确认的内容，替换前复核原文；无效范围或写入失败时不发送 |
| FR-07 | 单次发送 | 重复点击、长按或重复回调不能导致双发；授权与文本、会话、输入框及窗口实例绑定 |
| FR-08 | 错误恢复 | 超时、断网、读取失败、权限撤销显示明确状态，不自动放行或自动重发 |
| FR-09 | 用户控制 | 可取消检查、忽略建议、明确仍然发送和暂停保护；暂停状态清晰可见 |
| FR-10 | 隐私 | 默认不落盘聊天正文、不在日志输出原文；云端处理必须由用户明确选择 |
| FR-11 | 兼容范围 | 记录系统、架构、应用版本、发送模式和显示设置；未验证组合不得冒充支持 |

修正面板显示预览；采纳后若需恢复原文，必须仍匹配采纳后的快照，不能覆盖用户后续输入。不自动撤回已经发出的消息。

## 6. 明确不做

- 首版不覆盖语音、文件、图片、撤回、计划发送和手机短信。
- 不读取完整历史聊天、不自动代聊、不在后台批量发送消息。
- 不用 OCR 或固定屏幕坐标替代可靠的会话及文本识别。
- 不绕过 macOS 权限、Secure Input 或其他系统保护，不要求 root。
- 不把“宿主动作已触发”描述为“对方已收到”。

## 7. 可靠性与隐私边界

蒙版和事件拦截只能覆盖已适配入口；助手退出、崩溃或权限失效后保护可能消失。文本复核与宿主发送通常无法构成原子操作，仍存在竞态；必须通过真实应用验证缩小风险，不能作绝对安全保证。

服务故障时，助手不主动发送；用户仍可明确选择忽略检查或暂停保护。状态未知时不得自动重试宿主发送，避免重复消息。

复杂中文歧义及英语纠错通常需要真实校对引擎；简单本地规则仅是降级能力，不能宣传为完整离线校对。云端提供商、费用、保留策略、区域和密钥保管尚未选定，实施前需确认。凭据不得写入仓库或客户端安装包。

## 8. 交付与验证阶段

1. 可行性验证：在用户 Mac 上证明目标界面可读写、会话可区分、两类发送入口可接管。
2. 保护原型：完成状态机、蒙版、快捷键及确认面板；测试引擎仅用于演示，明确标注无真实校对能力。
3. 可用 MVP：接入经确认的校对引擎，通过三个语言场景及目标客户端真机验收。
4. 扩展与发布：验证其他客户端，落实签名、公证和更新流程；不把本地开发构建视为已上架产品。

语言效果使用人工标注的脱敏语料评估，不预先承诺未经测试的准确率或延迟。支持矩阵和未通过用例必须随代码保留。
